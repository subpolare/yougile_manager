# YouGile Telegram Digest Bot

Бот связывает Telegram-группу с одним проектом YouGile и отправляет свежую сводку
задач по будням в 12:00 по Москве. В личных чатах доступна добровольная подписка на
задачи сотрудника по всем подходящим проектам. Привязки создаются через Telegram и сохраняются в
MySQL. Бот работает одним экземпляром через long polling.

## Конфигурация

Обязательные значения в `.env`:

```dotenv
YOUGILE_COMPANY_ID=your-company-uuid
YOUGILE_API_KEY=your-api-key
TELEGRAM_BOT_TOKEN=your-telegram-token
```

`YOUGILE_COMPANY_ID` сохраняется в конфигурации, хотя рабочие API-запросы авторизуются
уже привязанным к компании ключом.

Сотрудники задаются парами с любым общим префиксом:

```dotenv
IVAN_YG=yougile-user-uuid
IVAN_TG=@telegram_username
```

`*_YG` — UUID пользователя YouGile, `*_TG` — Telegram username. Значение
`*_YG=unknown` означает, что YouGile-сопоставление пока неизвестно. Пустой или невалидный
`*_TG` игнорируется; в сводке тогда используется настоящее имя из списка пользователей
YouGile. Перечень сотрудников в коде не зашит.

`TELEGRAM_CHAT_EDITORS`, `TELEGRAM_CHAT_EDITING` и `TELEGRAM_CHAT_MANAGERS` зарезервированы
на будущее и сейчас не используются для маршрутизации.

## Запуск в Docker

Docker Compose поднимает MySQL 8.4 с постоянным томом `mysql_data`, ждёт успешного
healthcheck и только затем запускает бота. Устанавливать MySQL на компьютер не нужно.
Значения `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` и `MYSQL_ROOT_PASSWORD` можно
переопределить в `.env`; иначе используются безопасные локальные значения по умолчанию.

```bash
docker compose up -d --build
docker compose logs -f bot
```

Остановка:

```bash
docker compose down
```

Данные MySQL при обычном `down` сохраняются в именованном томе.

Локальный запуск тестов (MySQL и реальные ключи не требуются):

```bash
uv sync --all-groups
uv run pytest -q
```

Тесты используют SQLite только как изолированный async test double для репозитория;
рабочее приложение использует MySQL через `asyncmy`.

## Команды

- `/init 7` — найти единственный допустимый проект с заголовком, начинающимся на `#7`.
- `/init <точное полное название проекта>` — точное сопоставление без fuzzy-поиска.
- `/status` — показать текущую привязку чата.
- `/task` — вручную отправить групповую сводку; в личке — задачи текущего сотрудника.
- `/start` — в личке включить персональную рассылку по будням, без немедленного дайджеста.
- `/stop` — в личке отключить только автоматический YouGile-дайджест, сохранив доступ к `/task` и голосовые напоминания.

`/init` доступна любому участнику GROUP/SUPERGROUP, без проверки статуса администратора
и без вызова Telegram member/admin API. Любой участник может изменить привязку группы. Один чат связывается ровно с одним проектом, и один проект —
ровно с одним чатом; перемещения выполняются транзакционно. Источник истины — MySQL.

Допустимы только проекты, название которых начинается с `#<число>`. Проекты с префиксом
`#5 Голова` всегда исключены.

## Состав сводки

Учитываются только незавершённые, неудалённые и неархивные задачи с дедлайном из активных
досок и колонок выбранного проекта. Согласно актуальной
[REST API v2 документации YouGile](https://yougile.com/api/), клиент обходит пагинацию
`content`/`paging` (`limit`, `offset`, `next`), использует `/task-list` вместо устаревшего
списка `/tasks` и связывает иерархию project → board → column → task по ID.
В каждой строке сводки перед названием задачи указывается её колонка. Порядок досок и
колонок сохраняется из последовательности `content`, возвращённой API; внутри колонки
задачи идут по точному времени дедлайна, затем по названию.
Подзадачи из массива ID `subtasks` разрешаются по полной пагинированной выдаче
`/task-list` и показываются отдельными пунктами. Для них используются собственные
дедлайн, статус и исполнители; от родителя наследуется только контекст колонки, поскольку
YouGile не возвращает `columnId` у вложенных задач. В строке подзадачи указывается её
непосредственный родитель: `(подзадача внутри «Название родителя»)`.

Дедлайн — поле `deadline.deadline` (конечная дата диапазона). Timestamp переводится в
`Europe/Moscow`, затем задачи попадают ровно в одну группу:

1. сегодня;
2. после сегодня, но строго до ближайшего понедельника (завтра–воскресенье);
3. просрочено — строго до сегодня.

Автоматическая отправка групповых и личных сводок выполняется **понедельник–пятница
в 12:00 Europe/Moscow**. По выходным работает ручной `/task`. При запуске после
пропущенного времени бот не отправляет рассылку задним числом. Успешная отправка
фиксируется в `daily_dispatches`, поэтому перезапуск планировщика не создаёт повторную
автоматическую сводку за тот же московский день. Ручной `/task` эту таблицу не меняет.

## Личные дайджесты

При первом `/start` сотрудник определяется по парам `*_TG`/`*_YG`: `@` необязателен,
регистр username не учитывается, UUID должен быть валидным. `/task` и `/stop` до первого
`/start` не создают подписку. После регистрации источник истины — числовой Telegram ID
и сохранённый YouGile ID, поэтому смена username или удаление пары из `.env` не ломает
доступ. Один YouGile ID нельзя привязать ко второму Telegram ID через совпавший username.
Повторный `/start`, включая вызов после `/stop`, включает существующую подписку.

Личная сводка охватывает все текущие проекты workspace, независимо от `/init`.
Для названий с `#` используется часть до первого `/`; проекты со словами «Голова»,
«Шифры», «Растения», «Рак» в этой части исключаются (целое слово, без учёта регистра).
Текущее временное ограничение: проекты без начального `#` исключены (включая «Агргатные»).
Эти правила не меняют ограничения групповой привязки.

Перед задачей выводится название проекта, исполнители не показываются. У подзадачи
сохраняется непосредственный родитель. Собственные исполнитель, состояние и дедлайн
обязательны; поля родителя не подставляются. В каждой секции сортировка идёт по точному
дедлайну от раннего к позднему, включая просрочку. Будущие даты — `DD.MM`, просроченные —
`DD.MM.YYYY`. Даже пустая личная сводка содержит приветствие и подсказку `/stop`/`/task`.

При старте приложения `create_all` добавляет две таблицы без изменения старых данных:

- `personal_digest_subscriptions`: Telegram ID (PK), уникальный YouGile ID, текущий
  username, `enabled`, даты создания и изменения. `/stop` не удаляет строку.
- `daily_digest_greetings`: московская дата (PK), выбранное приветствие, дата создания.
  Конкурентные первые запросы используют одну победившую запись. Все ручные и
  автоматические, групповые и личные сводки получают приветствие через один провайдер.

На автоматический запуск выполняется один полный пагинированный снимок
`/projects`, `/boards`, `/columns`, `/task-list`, `/users`; личные задачи индексируются по
собственным исполнителям один раз. Ошибка API не превращается в пустой дайджест.
Ошибка доставки одному подписчику не мешает остальным и не отправляется в группы.
Запись в общем `daily_dispatches` создаётся только после успешной отправки всех частей,
под блокировкой строки адресата. Как и раньше, при частичном сетевом сбое повторная
попытка может повторить уже доставленные части: Telegram не поддерживает транзакцию
на несколько сообщений. Бот рассчитан на один экземпляр long polling.

## Личные голосовые напоминания

Известный по `*_TG`/`*_YG` или постоянной Telegram-привязке сотрудник может отправить
боту русское **голосовое сообщение в личку**, даже до `/start` или после `/stop`.
Одно голосовое создаёт одно активное напоминание, отдельное от задач YouGile.

Настройки в `.env` (ключ не попадает в репозиторий):

```dotenv
OPENAI_API_KEY=your-openai-api-key
OPENAI_TRANSCRIPTION_MODEL=gpt-transcribe
OPENAI_REMINDER_MODEL=gpt-5.6-luna
OPENAI_ERROR_MODEL=gpt-5.6-terra
# ERROR_ADMIN_TELEGRAM_USER_ID=<numeric Telegram user ID>
```

Оригинальный OGG/Opus скачивается во временный файл и распознаётся через официальный
асинхронный SDK (`languages=["ru"]`). Файл удаляется в `finally`. Luna получает русскую
расшифровку и текущую календарную дату `Europe/Moscow` в ISO, русском формате и с днём
недели. Она убирает разговорный шум и привязывает относительные даты к абсолютным.
Ответ проверяется через `responses.parse` и Pydantic; максимум 1500 символов.
Luna и Terra **всегда** вызываются с `reasoning={"effort": "none"}`, `store=False`.
Без OpenAI-ключа существующие дайджесты и доставка сохранённых напоминаний продолжают
работать; создание голосовых требует настройки ключа.

Напоминание сразу сохраняется. Ответ на исходное голосовое предлагает:

- **✅ Ок** — убрать кнопки; напоминание уже активно.
- **✍️ Изменить** — следующая обычная текстовая реплика заменяет формулировку без LLM.
  Команды не считаются новой формулировкой; оригинальная расшифровка не меняется.
- **❌ Удалить** — физически удалить напоминание и связанные записи.

Редактирование хранится в MySQL и действует 15 минут. Можно оставить прежний текст или
отменить напоминание целиком. Новое редактирование закрывает предыдущее без удаления
его напоминания. Минутное задание проверяет UTC `expires_at`, в том числе сразу после
перезапуска; по истечении срока остаётся прежний текст и приходит уведомление.

По будням в **12:00 Москвы** каждое активное напоминание приходит отдельным сообщением
`📝 …`, от старых к новым. Если включён личный YouGile-дайджест, напоминания следуют
сразу за ним. **`/stop` влияет только на YouGile**. Личный `/task` сначала пытается
показать YouGile, затем отправляет все напоминания, в том числе в выходные.
Сбой YouGile не блокирует напоминания ни в планировщике, ни в `/task`.

Отправь **`/done` ответом на любую ранее доставленную копию** активного напоминания.
Удаляются строка напоминания, расшифровка, текст, все соответствия Telegram-сообщений
и сессия редактирования. Архива выполненных напоминаний нет. Это удаление данных
бота из активной БД; ранее отправленные сообщения в истории самого Telegram остаются.

При запуске `create_all` без разрушения старых данных добавляет:

- `voice_reminders` — активные напоминания, исходная расшифровка, текст и ID голосового;
- `reminder_deliveries` — много сообщений на одно напоминание, FK `ON DELETE CASCADE`,
  уникальные `(chat_id, message_id)` и `(reminder_id, scheduled_date)`;
- `reminder_edit_sessions` — максимум одна сессия на Telegram-пользователя,
  FK `ON DELETE CASCADE`, время истечения UTC;
- `error_admin_targets` — постоянный числовой адрес администратора, отдельно от подписок.

Для автоматических отправок фиксируется московская дата, для ручных — NULL, поэтому
повторный `/task` разрешён и не расходует автоматическую доставку. Транзакция с
блокировкой владельца через MySQL `GET_LOCK` сериализует отправку, изменение и удаление.
Блокировка освобождается на том же соединении после commit; постоянных записей блокировок
нет. При аварии между успешным Telegram-send и commit возможен повтор, как у существующего
дайджеста: транзакцию между MySQL и Telegram бот не обещает.

Технические ошибки обрабатывает `ErrorReporter`. Terra получает только тип ошибки,
безопасные HTTP/системные коды, компонент, операцию, числовые ID и короткий стек без
исходных строк/локальных переменных. Сырые сообщения исключений намеренно скрыты:
они могут содержать тело запроса или SQL-параметры. Дополнительный sanitizer скрывает
ключи, Bearer, токены, URL и пароли. Расшифровки, аудио и тексты напоминаний не логируются
и не передаются в отчёты. Нормальная валидация пользователя не вызывает Terra.

Отчёт направляется @subpolare **по числовому ID**: явная настройка имеет приоритет,
иначе используется постоянная запись или существующая личная подписка. Входящее личное
сообщение @subpolare позволяет запомнить ID без включения подписки. После привязки
числовой ID авторитетнее сменившего владельца username. Если адрес не найден, стартовый
лог явно сообщает `ERROR ADMIN UNRESOLVED`.
При отказе Terra локальное уведомление содержит оба типа ошибок; при отказе Telegram
остаётся локальная запись, без рекурсивных запросов.

Тесты OpenAI и Telegram полностью замоканы: `pytest` не расходует API-кредиты.
Проверка на MySQL: `REMINDER_MYSQL_TEST_URL` можно задать URL **отдельной тестовой БД**;
интеграционные тесты создают и удаляют только свои случайно адресованные строки.

## Голосовые черновики задач для `SASHA_TG` и `VLAD_TG`

Сотрудники, разрешённые существующей системой `*_TG` / `*_YG` через
`SASHA_TG` или `VLAD_TG`, получают в личном чате единый поток голосовых задач. Сохранённая
Telegram-привязка имеет приоритет над изменившимся username. У остальных
сотрудников голосовые напоминания работают как прежде.

`gpt-transcribe` расшифровывает голосовое по-русски. `gpt-5.6-luna` возвращает
Structured Output `{title, deadline}` с текущей датой Europe/Moscow,
`reasoning.effort=none`, `store=false`. Дедлайн убирается из заголовка;
неуверенная или отсутствующая дата возвращается как `null`. Проект и исполнителей
модель не выбирает. Terra и существующая очистка технических ошибок не меняются.

Черновик сохраняется в существующей таблице `voice_task_drafts`, отдельно от активных
`voice_reminders`. Он не попадает в `/task` или рассылку. Ответ на исходное
голосовое содержит четыре кнопки: «✅ В YouGile», «📝 Напомнить тут»,
«✍️ Изменить», «❌ Удалить». До выбора ничего не создаётся автоматически.

- **В YouGile:** проект определяется серверной конфигурацией `VOICE_TASK_PROJECTS`:
  `SASHA` → `ONLY Саша`, `VLAD` → `ONLY Влад`; колонка для обоих — `Задачи из бота`.
  Сопоставление по точному названию после trim; удалённые/архивные сущности
  исключаются. Имеющаяся колонка используется повторно. Новая создаётся лишь
  при единственной активной доске проекта. Неоднозначность идёт в ErrorReporter.
  Задача передаётся с **`assigned: []`**, без ответственных: ни `SASHA_YG`, ни `VLAD_YG` не передаются в исполнителях.
  Дедлайн — timestamp московской полуночи в миллисекундах, `withTime: false`;
  календарная дата совпадает с датой, используемой текущим дайджестом.
- **Напомнить тут:** в одной транзакции создаётся обычное голосовое напоминание
  с исходными voice IDs, расшифровкой и текстом с русской датой, затем черновик
  физически удаляется. Дальше действуют существующие доставка, `/task`, история
  сообщений и `/done`.
- **Изменить:** сохраняется 15-минутная сессия. Следующее обычное личное сообщение
  заново обрабатывает тот же Luna extractor. Исходная расшифровка остаётся прежней.
  Техническая ошибка сохраняет предыдущий результат и возможность повторить ввод.
- **Удалить:** физически удаляются черновик и его сессия; ответ на исходное
  голосовое — «Окей, забыл об этом».

При отсутствии дедлайна вместо кнопок запрашивается строго `DD.MM.YYYY`.
Календарная валидность проверяется Python, без LLM. Неверный ввод не продлевает
сессию. Команды сохраняют приоритет. Таблица `voice_task_draft_sessions` хранит
одну сессию `deadline` или `edit` на пользователя с UTC `expires_at`; вместе
с прежними edit-сессиями обеспечивается один активный свободный ввод на пользователя.
Обе таблицы создаются штатным `initialize_database` / `create_all` при старте.

Существующая ежеминутная очистка (также сразу после запуска) удаляет просроченный
незавершённый черновик и расшифровку и отправляет «Время вышло, задачу не создал».
При таймауте редактирования полного черновика возвращается прежнее подтверждение.
Замена сессии сохраняет полный черновик с кнопками, а недоступный незавершённый
черновик физически удаляет. Таймеров `asyncio.sleep()` на пользователя нет.

Все изменения используют существующую блокировку владельца, включая MySQL
`GET_LOCK`. Текущий [Swagger YouGile v2](https://yougile.com/api-v2)
([JSON](https://yougile.com/api-json), проверен 2026-09-15) документирует
`idempotencyKey` в `CreateColumnDto` и `CreateTaskDto`. Для колонки ключ стабилен
по проекту, для задачи случайный UUID сохраняется в черновике до первого POST.
Повторные запросы и перезапуски используют тот же ключ, а колонка перечитывается
после создания. Новые запросы используют прежние авторизацию, limiter и retry.

Черновик удаляется только после подтверждённого успешного POST. При ошибке он
сохраняется для повторного нажатия; пользователю показывается безопасный текст,
администратору — централизованный ErrorReporter. После успеха в БД не остаются
заголовок, расшифровка, дата или сессия черновика. История/аналитика черновиков
не ведётся. Существующий фильтр проектов личного дайджеста сохранён.

Расширение на Влада использует те же сервис, обработчики, таблицы и сессии; миграция
или удаление существующих черновиков Саши не нужны. На каждом callback проект
вычисляется заново через стабильную идентичность отправителя и серверную конфигурацию,
после чего проверяется владение черновиком. Callback содержит только действие и ID.
Конфликтующие идентичности не получают доступ. Фильтры личного/группового дайджеста
не меняются. Нужный проект должен уже существовать; runtime создаёт только колонку
при однозначной активной доске. Минимальная структура для Влада повторяет доску
`Задачи от бота` и колонку `Задачи из бота`, без задач, файлов или комментариев Саши.
